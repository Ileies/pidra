Complete product and architecture plan for the morning briefing system

What this system is

A fully automated morning briefing engine that ingests newsletters, personal emails, SMS, calendar events, and your to-do list — then produces a single daily report split into two sections: world intelligence and personal action center. It has long-term memory, knows when to ask you questions before proceeding, and uses your local Ollama instance to do the heavy lifting before handing a compact, high-density payload to Sonnet 4.6 for final synthesis.

The two-section model

Section 1 — intelligence briefing
Everything you couldn't have known without doing research. Newsletter content, geopolitical events, AI breakthroughs, market shifts, science milestones. Organized by topic, not by source. Cross-referenced with previous reports. Never repeats old news — only updates and novelties.
Section 2 — personal action center
Your life logistics. Emails requiring response, payment deadlines, invitations, tasks approaching due date, SMS that need follow-up, calendar events next week with context. Prioritized by urgency. Cross-linked to calendar and to-do list so items already logged are not repeated.

Core design decisions

Why not one huge prompt?
32 newsletters at ~1,200 tokens each = ~38,000 tokens of raw email content — before personal emails, SMS, or context. At 200K context that fits, but Sonnet 4.6's output quality degrades badly when the input is mostly noise. More importantly: you'd pay to process promotional footers, unsubscribe links, and repeated boilerplate. The Ollama pre-processing layer eliminates ~60–70% of tokens before Sonnet ever sees the data.
Why not vector stores?
Correct instinct. With cosine similarity thresholds you will silently drop information — a story that's phrased unusually, a niche topic in an unfamiliar domain, or a low-similarity item that is actually the most important thing that day. For a daily briefing where completeness matters, explicit structured extraction beats probabilistic retrieval every time.
Why not summarize each newsletter with Sonnet?
Not cost — at your usage level that's maybe $3/month extra. The real problem is latency: 32 sequential Sonnet calls would take 3–5 minutes. With Ollama running locally and parallelized, those 32 extractions finish in ~45 seconds with zero API cost. Sonnet is reserved for the one task where its reasoning quality actually matters: final synthesis and judgment.

Full execution pipeline

All phases run in Bun. Phases 1–3 are fully parallel. Phase 4 is a conditional gate. Phases 5–6 run after the gate resolves.

Phase 1 — parallel ingestion
Fetch all sources simultaneously
One Promise.allSettled launches all source fetches at once. Each source is isolated — a failed IMAP poll doesn't block the calendar fetch. Failures are logged and noted in the report ("3 newsletters unavailable today").

For personal emails: extract type, urgency, required action, unknown-context flag. Output is structured JSON. All calls fire in parallel — limited to 4 concurrent by your server's RAM.

The local AI layer

Ollama is not a fallback — it's the workhorse. By the time Sonnet sees any data, Ollama has already compressed, structured, and filtered everything. This is the architectural decision that makes the whole system economically trivial and fast.

Recommended model

qwen2.5:14b — primary recommendation
Stronger multilingual ability (important for your German newsletters and potential Chinese sources). Excellent at structured JSON extraction. Better reasoning than llama3.1:8b for edge cases. Runs comfortably on your server if you have 16GB+ VRAM or 32GB RAM.
llama3.1:8b — if RAM-constrained
Fast, reliable, cheap on RAM. Good at classification and extraction tasks. Will occasionally miss nuance in long analytical essays (Astral Codex Ten, Not Boring). Acceptable fallback if 14b is too slow for your server.

What Ollama does per item

Newsletter extraction prompt (structured JSON output)
Extract from this newsletter email. Return ONLY valid JSON: { "source": "newsletter name", "items": [ { "headline": "one sentence max", "topic_tags": ["AI", "China", "finance", ...], "key_claim": "the actual claim or finding, 2 sentences max", "entities": ["person/org/place names"], "novelty": "new|continuation|repeat", "relevance_score": 1-5 } ], "skip_reason": null or "promotional|duplicate|off-topic" }
Personal email classification prompt
{ "type": "invoice|invitation|reply_needed|automated|spam|personal|legal|unknown", "urgency": "critical|high|normal|low", "deadline": "ISO date or null", "action_required": "one sentence or null", "unknown_context": true/false, "question_for_user": "what do you need to know? or null", "sender_known": true/false }

What Ollama does NOT do

Don't ask Ollama to write prose, make judgments about geopolitical significance, or synthesize across sources. Its job is purely structural: compress text → JSON, classify, flag. When you ask it to write "a summary of what matters today in AI", the output quality is unreliable and you lose the structured data you need for Sonnet's prompt. Keep Ollama as a lossless compressor, not an analyst.

Parallelization strategy

Run Ollama calls with a concurrency limit of 4 (adjust based on your server specs). With 32 newsletters + ~20 personal emails = ~52 calls. At ~2 seconds each with concurrency 4, this finishes in roughly 26 seconds wall time. Use Bun's Promise.allSettled with a simple semaphore. Failed calls fall back to passing the raw email text directly to Sonnet with a note: "Ollama extraction failed — raw content follows."

Context management strategy

This is the hardest part of the system. The goal: Sonnet should always know what happened recently, never repeat itself, but also never silently drop a continuing story just because it was mentioned yesterday.

The active topics table

Every story that appears in the report gets written to an active_topics table. This is the core of your cross-day memory. It stores:

What goes into Sonnet's context payload

Context block fed to Sonnet (Section 1 synthesis)

1. Active topics: all stories from the last 14 days with their running_summary. These go first — Sonnet must update them, not re-introduce them.

2. Today's extractions: structured JSON from Ollama, relevance-scored, novelty-flagged. Only items with relevance ≥ 3 and novelty = "new" or "continuation" are included. Relevance 1–2 items are silently dropped.

3. Your profile block: a compact 200-token profile telling Sonnet what you care about (see Prompt Engineering tab).

4. Light day / heavy day signal: a computed integer — "today has 12 high-relevance items" vs "today has 47". Sonnet uses this to calibrate depth vs breadth.

Handling variable daily volume

Light days (<10 high-relevance items)
Instruct Sonnet to go deeper on fewer stories. Include more context about ongoing topics. Acceptable to include relevance-3 items that would be cut on heavy days. Report is shorter but denser per topic.
Heavy days (>30 high-relevance items)
Hard cap: include only top 20 by relevance score. Instruct Sonnet: "this is a high-volume day — prioritize ruthlessly. Items below the cut should be listed in a brief 'also noted' section with one line each."

The notes store

The system can write free-form notes to a notes table at any time — including after the report is delivered. Use cases: "User asked me not to include Miles & More promotional emails." "User confirmed that [company X] is a client — treat emails from them as high-priority." "Ongoing: user is negotiating with [party Y] — flag any related news." Notes are retrieved in full on every run (they should stay small — prune aggressively).

Known contacts table

Built over time as you answer the question gate. Starts empty. After 2 weeks of use, Sonnet will know that "sarah@startup.ch" is a potential investor, "lina@firma.de" is your girlfriend's colleague, etc. This eliminates repeat questions about the same senders and personalizes urgency scoring.

The question gate

The most important UX innovation in this system. Instead of silently proceeding with wrong assumptions, the tool pauses and asks you — but only when it genuinely doesn't know, and only once per run, batched.

Triggering conditions

Unknown sender
Email from someone not in the contacts table and not inferable from domain. Question: "Email from jan@innovate.io with subject 'Partnership proposal' — who is this?"
Ambiguous action
Email that requires a decision but the context is missing. "Reply from [known contact] about meeting timing — do you want this added to your calendar?"
Unusual financial item
Invoice or payment request from an unknown party. Never assumed to be valid — always flagged.
SMS from unknown number
Any SMS not in the known contacts table. Context question asked before classification.

Question batching and format

POST /api/questions { "run_id": "2025-05-06-morning", "timeout_minutes": 45, "questions": [ { "id": "q1", "item_type": "email", "from": "alex@neuralbridge.io", "subject": "Following up on our conversation", "question": "Who is Alex from NeuralBridge? Should this be treated as a lead, a partner inquiry, or personal?" }, { "id": "q2", "item_type": "sms", "from": "+41 79 123 4567", "preview": "Hey, confirmed for Thursday", "question": "Who is this contact? What's being confirmed for Thursday?" } ] }

Parallelization during the wait

Section 1 (intelligence briefing) does not wait. It starts immediately after Phase 3 completes regardless of whether questions are pending. Only Section 2 (personal action center) blocks on the gate. In most cases, Section 1 finishes and is ready to deliver while you're still answering the questions. Final delivery is: both sections together once the gate resolves.

Timeout behavior

If no answer arrives within 45 minutes, Section 2 proceeds with explicit gap notes:

⚠ Unresolved context (question unanswered): Email from alex@neuralbridge.io classified as "unknown" — included below without personalized context. Please respond to pending question to update contact profile.

Contact learning loop

Every answered question writes to the contacts table. After ~2 weeks, question rate drops to near zero for existing contacts. New contacts still trigger the gate. This is your system learning your social graph over time with zero explicit configuration.

Prompt engineering

Two distinct system prompts. Each is compact by design — Sonnet's intelligence needs direction, not walls of instruction.

Your profile block (shared by both prompts, ~200 tokens)

You are compiling a personal morning briefing for a single reader. You do not know anything about the reader except what the input gives you - their identity, interests and priorities arrive in the payload at runtime. Priorities, in order of importance for the intelligence section:

1. AI/LLM breakthroughs, model releases, capability jumps, policy
2. China — geopolitics, tech sector, US-China dynamics, domestic policy
3. European/Swiss startup ecosystem, VC funding, regulation
4. Global macro: interest rates, currency, geopolitical crises affecting tech
5. Neuroscience and BCI milestones
6. Science breakthroughs (physics, biology, longevity)
7. Software engineering: major framework releases, security events

Exclude: celebrity, sports, US domestic politics unrelated to tech/China, promotional content, anything below relevance 3. He reads fast and thinks faster — be dense, not gentle. No padding sentences.

Section 1 synthesis prompt (intelligence)

Ongoing stories (update, do not re-introduce): [active_topics JSON]
Today's extracted items: [ollama_extractions JSON — relevance ≥ 3 only]
Volume signal: [N] high-relevance items today. [light/normal/heavy] day.

Write Section 1 of today's briefing. Rules:
— Group by domain, not by source. Never mention which newsletter a story came from.
— For ongoing stories: start with "UPDATE:" and reference how it has developed. Do not re-explain the background.
— For new stories: introduce concisely, state the key claim, state why it matters to me.
— If 3+ sources covered the same story, note the cross-source weight: "(covered by 4 sources)".
— Heavy days: ruthless top-20 cut, then one-line "also noted" section.
— Target length: 600–900 words regardless of volume.

Section 2 synthesis prompt (personal)

Personal email/SMS extractions: [ollama_extractions JSON]
Question answers received: [answered_questions JSON or "none pending"]
Calendar — next 7 days: [calendar JSON]
To-do list — all items: [todo JSON]
Known context: [relevant notes + contacts]

Write Section 2 of today's briefing. Rules:
— Group by urgency: Critical (deadline within 24h or requires same-day action) → High → Normal.
— For each item: state what it is, what action is required, and when by.
— Cross-reference: if an email relates to a calendar event, say so explicitly.
— If a to-do item already captures an email's action, note it as "already logged in your to-do" — don't duplicate.
— Flag any item that should be added to the calendar or to-do list and hasn't been yet.
— If the intelligence section mentioned something directly relevant to a personal item, link them.

What the output format should look like

Specify an explicit output structure in both prompts. Example: ## Intelligence briefing — [date]\n### AI & technology\n...\n### Also noted\n...\n---\n## Personal action center\n### Critical\n...\n### High priority\n.... Consistent structure means your report reader (SvelteKit dashboard or whatever you build) can parse sections programmatically.

Scaling considerations

If you add more sources later
Cost scales almost entirely in the Ollama layer (free) until you have so many sources that the Sonnet payload grows. At 100 newsletters you'd still be under $0.20/day because Ollama's compression ratio improves with volume — more items means more get filtered as low-relevance.
Active topics growth over time
The active_topics payload grows as more long-running stories accumulate. Prune stories with status "resolved" or last_updated > 30 days. In practice, at steady state you'll have 20–40 active topics, adding ~3–4K tokens to every run — acceptable.

Haiku as a middle tier (optional)

If you ever want to add a mid-step quality check between Ollama and Sonnet — for example, re-scoring relevance on Ollama extractions you're not confident about — Claude Haiku ($0.80/M input) is 4x cheaper than Sonnet for mechanical validation tasks. Not necessary at current scale, but worth knowing as an upgrade path.
